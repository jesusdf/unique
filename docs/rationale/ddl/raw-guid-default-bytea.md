# Oracle `RAW(16) DEFAULT SYS_GUID()` → PostgreSQL `BYTEA` with a matching `DECODE(...)` default

**Problem.** `RAW(16) DEFAULT SYS_GUID()` is Oracle's idiom for a
binary-GUID primary key: `SYS_GUID()` generates a 16-byte raw value used
directly as the default. `RAW` maps to PostgreSQL's `BYTEA`, but
PostgreSQL's own GUID generator, `gen_random_uuid()`, returns a `uuid`
value — a type PostgreSQL's `BYTEA` column rejects outright as a default
(error 42804, "column is of type bytea but default expression is of type
uuid"), even though both represent the same 16 bytes conceptually.

**Solution.**

```sql
-- tests/integration/test_oracle_source_m4_wave.py::TestRawGuidDefaultOnPg
CREATE TABLE h_x (IDL RAW(16) DEFAULT SYS_GUID() NOT NULL, LANG VARCHAR2(5));
-- oracle -> postgresql:
CREATE TABLE h_x (
  IDL BYTEA NOT NULL DEFAULT DECODE(REPLACE(gen_random_uuid()::TEXT, '-', ''), 'hex'),
  LANG VARCHAR(5)
);
```

A `SYS_GUID()` default on a *non*-binary column (`VARCHAR2(36) DEFAULT
SYS_GUID()`, where the GUID is meant to be stored as text) is left with a
text-typed default instead — no `DECODE`/`BYTEA` conversion, since there is
no byte-vs-text mismatch to bridge there.

**Discussion.** The column's own target type decides which of Oracle's two
different `SYS_GUID()` idioms applies: a `BYTEA` column needs a value that
*is* bytes, so `gen_random_uuid()`'s `uuid` result is cast to text, has its
hyphens stripped (`uuid`'s canonical text form is hyphenated, `SYS_GUID()`'s
raw bytes are not), and is decoded from its hex digits into `BYTEA` via
`DECODE(..., 'hex')` — reproducing the same 16 raw bytes a `RAW(16)`
column expects, generated by PostgreSQL's own native random-UUID source
rather than inventing a byte generator from scratch.

> **Note** faithful — live-verified the `BYTEA` column accepts the
> synthesized default and stores 16 random bytes on every insert, matching
> `SYS_GUID()`'s own contract; the non-`BYTEA` leg is untouched because
> there is nothing to bridge. No warning.
