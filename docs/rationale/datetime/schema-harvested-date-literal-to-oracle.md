# An ISO date/timestamp string written into a harvested `DATE`/`DATETIME` column → wrapped in an Oracle ANSI literal

**Problem.** `INSERT INTO evt (d, ts) VALUES ('2024-01-15', '2024-01-15
10:30:00')` relies on the target column's own declared type
(`DATE`/`DATETIME`) to interpret a plain ISO string as a date or
timestamp — T-SQL, PostgreSQL, and MySQL all accept this implicit
string-to-date coercion. Oracle does not: a bare string literal written
where a `DATE`/`TIMESTAMP` column is expected raises `ORA-01861`, "literal
does not match format string," unless it is explicitly typed with `DATE
'...'`/`TIMESTAMP '...'`.

**Solution.**

```sql
-- tests/unit/core/test_transpiler.py::TestOracleDateLiterals
CREATE TABLE dbo.evt (
  id INT IDENTITY(1,1) NOT NULL,
  d DATE NOT NULL,
  ts DATETIME NULL
);
INSERT INTO dbo.evt (d, ts) VALUES ('2024-01-15', '2024-01-15 10:30:00');
-- tsql -> oracle:
CREATE TABLE evt (
  id NUMBER(10) GENERATED BY DEFAULT AS IDENTITY,
  d DATE NOT NULL,
  ts TIMESTAMP
);
INSERT INTO evt (d, ts)
VALUES (DATE '2024-01-15', TIMESTAMP '2024-01-15 10:30:00');
```

`UPDATE`s onto the same harvested columns get the same treatment; a string
literal written into a column with no known `DATE`/`TIMESTAMP` type (no
matching `CREATE TABLE` in the script, or a genuinely `VARCHAR` column) is
left as a plain string, since there is no schema information to wrap it
against.

**Discussion.** Unique harvests every `CREATE TABLE`'s column types before
translating the script's DML, the same registry the bare-`NUMBER`
role-aware mapping and several other cross-statement mechanisms on this
page rely on. An `INSERT`/`UPDATE` literal is only wrapped once its target
column is confirmed `DATE` or a timestamp type from that registry — the
other three engines never need this, since their own implicit string
coercion already does the same interpretation Oracle's explicit literal
does here.

> **Note** faithful — the wrapped literal parses to the identical date/time
> value the implicit coercion would have produced on the other targets; no
> warning, since this is purely a syntactic requirement Oracle imposes,
> not a value change.
