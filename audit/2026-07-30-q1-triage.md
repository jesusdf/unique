# Q1 triage — Oracle-source / MySQL-source procedural degrade rate on the PG pivot

Analysis-only pass over `docs/TODO.md`'s Q1 entry. No `src/` changes. Method,
raw data, and reproduction script are below; findings are ranked by
routines-affected (raw) and by routines-actually-unblocked (the more useful
number, once inherited/pre-existing markers are separated from genuinely new
degrades).

**Corpus and measurement:** HEAD `75dd020`. `tests/fixtures/procedures/`
routines split via `unique.core.batch_splitter.BatchSplitter` (the same
splitter the fixture-family tests use), filtered to `PROCEDURAL` batches
containing a `CREATE [OR REPLACE] PROCEDURE|FUNCTION` (a batch may carry
leading companion DDL — e.g. a table-variable-derived `CREATE GLOBAL
TEMPORARY TABLE` — folded in by the splitter's PL/SQL-block heuristic; the
routine name is the *last* match in the batch, not the first token). Each
routine transpiled standalone (oracle→postgresql, mysql→postgresql) via
`unique.core.transpiler.Transpiler().transpile(...)`. A routine is
**DEGRADED** if any `UNIQUE-NNNN` code appears in `result.warnings[].code` or
in the output text (`UNIQUE-\d{4}` regex, to catch carriers no warning
object covers).

**Important correction to a naive count:** `procedures_oracle.sql` and
`procedures_mysql.sql` are *themselves generated from the T-SQL fixture by
the transpiler* (see `tests/fixtures/procedures/SOURCES.md`), so they already
carry `UNIQUE-NNNN` comments baked in from that earlier T-SQL→Oracle /
T-SQL→MySQL generation step (e.g. `/* UNIQUE-1193: SET NOCOUNT ON --
tsql-only, no oracle equivalent */`). The project's own
`ProceduralTransformer._transform_comment` carries these forward unchanged
when the current transpile isn't back to their `restore_dialect` — correctly,
since PostgreSQL doesn't have `SET NOCOUNT` either. Counting every
`UNIQUE-NNNN` in the output therefore conflates two very different things:
degrades **inherited** from the fixture's own generation (correct,
permanent, out of scope for an oracle→pg / mysql→pg fix) versus degrades
**newly introduced** by *this* transpile step (the actual Q1 target). Every
routine below is measured both ways: `source_codes` = codes already present
in the routine's own source text before this transpile; `new_codes` =
output codes not in `source_codes`.

## Findings (top codes, mechanism + feasibility)

### Finding A — UNIQUE-1151: missing builtin/type mappings for the postgresql pivot (24 routines, 14 oracle + 8 mysql go fully CLEAN if fixed alone)

`rationales.py:359` names this the intentional, correct "general
unmapped-built-in gate" — when it fires it *should* fire (shipping invalid
SQL would be worse). The triage found exactly **five** distinct concrete
reasons behind the 24 occurrences (`transpiler` output, `UNIQUE-1151: output
failed the postgresql validity check (<reason>)`):

- `source-dialect leftovers: FROM DUAL` — Oracle's `SELECT ... FROM DUAL`
  survives into a fragment the validity check rejects.
- `source-dialect leftovers: SYS_REFCURSOR` — Oracle's ref-cursor type
  leftover (PostgreSQL's `refcursor` is the direct equivalent).
- `source-dialect leftovers: SYS_REFCURSOR, FROM DUAL` — both together.
- `untranslated mysql built-in ROW_COUNT(` — MySQL's `ROW_COUNT()`.
- `untranslated oracle built-in NUMTODSINTERVAL(` — Oracle's numeric→interval
  function (e.g. `SYSDATE + NUMTODSINTERVAL(-3, 'DAY')`).

**Feasibility — genuinely feasible, not a fundamental gap.** `FROM DUAL`
stripping already has a working pass at the top-level `SelectStatement`
recursion (`src/unique/core/transformer.py:2751`, docstring cites "audit
2026-07-08, D3" for exactly this fix) — the 1151 occurrences are fragments
that path doesn't reach: `_emit_embedded_dml` (`src/unique/core/procedural/
emitter/base.py:2117`) ships `EmbeddedDML.sql` **raw**, i.e. these fragments
never go through the sqlglot AST transform at all. This is the same
"SQL-embedded-as-text vs IR" gap already on record as the highest-leverage
remaining front from the challenge-corpus campaign — Q1 independently
reproduces it via a completely different corpus. `SYS_REFCURSOR`→`refcursor`
and MySQL `ROW_COUNT()`/Oracle `NUMTODSINTERVAL()` are ordinary
missing-builtin-mapping entries (see `src/unique/core/mappings.py`,
`src/unique/core/builtins.py` for the existing registry pattern) — the same
class of fix as any other unmapped-builtin backlog item, just not yet done
for these four.

### Finding B — UNIQUE-1171: `@`-inside-a-comment false positive (12 mysql routines, single-line fix)

`_find_user_var` (`src/unique/core/transformer.py:1897`, called from
`_gate_mysql_user_var` at line 1866) scans a `RawSQL`/`PassthroughSQL`
node's raw `.sql` text with `_USER_VAR_RE = re.compile(r"(?<!@)@(\w+)")`
after scrubbing **string literals** only:

```python
scrubbed = re.sub(r"'(?:[^']|'')*'", "''", value.sql)
m = self._USER_VAR_RE.search(scrubbed)
```

It does **not** scrub comments. Every routine in this corpus that used
T-SQL's `SET ROWCOUNT @col_2` carries the inherited carrier comment `/*
UNIQUE-1193: SET ROWCOUNT @col_2 -- tsql-only, no mysql equivalent */` from
the earlier T-SQL→MySQL generation. When that comment (now inside a
`RawSQL`) is re-scanned during mysql→postgresql, the `@col_2` **inside the
comment text** matches, and `_gate_mysql_user_var` degrades the **entire
routine** to a carrier — even though there is no actual MySQL `@`-variable
reference anywhere in the executable code. Confirmed live: `proc_1`'s only
`@` in the whole routine is inside that one comment; the routine is
otherwise ordinary MySQL DML that transpiles cleanly.

This directly violates the project's own "comments are trivia" rule (this
repo's `skills/SKILL-development-workflow.md` architecture guardrail) — the
scan should exclude `/* ... */` and `-- ...` spans exactly as it already
excludes string literals. **Feasibility: high — a bounded, single-function
fix** (mirror the existing string-literal-scrub pattern for comments, most
likely reusing whatever comment-stripping utility the rest of the codebase
already has for other text-scanning gates — worth checking
`_find_unknown_sysvar`, `src/unique/core/transformer.py:1929`, for the same
gap before fixing, since it has the identical shape).

### Finding C — UNIQUE-1033: `SQL%ROWCOUNT` used inline, not top-level (8 oracle routines, all go fully CLEAN if fixed alone)

Sample: `IF 0 /* UNIQUE-1033: SQL%ROWCOUNT has no top-level postgresql
equivalent */ <> 1 THEN`. The diagnostic's own wording ("no **top-level**
equivalent") already names the real constraint: PostgreSQL's equivalent,
`GET DIAGNOSTICS x = ROW_COUNT;`, is a **statement**, not an expression, so
it cannot be substituted inline into `IF SQL%ROWCOUNT <> 1 THEN`.

**Feasibility — feasible, substantial existing machinery to extend.**
`src/unique/core/procedural/transformer/base.py:3423-3497` already has a
full GET-DIAGNOSTICS-item mapping table and a working transform for the
*standalone-assignment* case (`x := SQL%ROWCOUNT;` → `GET DIAGNOSTICS x =
ROW_COUNT;`). What's missing is the **inline/expression** case: hoist a
synthetic `GET DIAGNOSTICS __rc = ROW_COUNT;` statement immediately before
the statement that references `SQL%ROWCOUNT` mid-expression, then substitute
the variable in place. `src/unique/core/procedural/transformer/_expr.py:151`
(`_ROWCOUNT_FN_EXPR = {"tsql": "@@ROWCOUNT", "oracle": "SQL%ROWCOUNT"}`)
notably has **no `"postgresql"` entry** — the expression-form substitution
table was never extended to the pivot target, which is the direct cause.

### Finding D — UNIQUE-1170: parser gives up on the temp-table-derived shape (4 oracle routines: proc_2, proc_7, proc_8, proc_9)

All four share the same shape: a T-SQL table variable, converted to an
Oracle `CREATE GLOBAL TEMPORARY TABLE ... ON COMMIT DELETE ROWS;` ahead of
the procedure (`UNIQUE-1196`), followed by a procedure body that reads/writes
it. Something inside that body's specific statement sequence trips the
procedural parser's `RawSQL(reason="Could not parse procedural construct")`
fallback (`src/unique/core/procedural/emitter/base.py:2141`), and the
degrade currently swallows the **entire routine** starting from that point
(observed carrier includes the temp table DDL and the `CREATE PROCEDURE`
header itself, re-commented). Not narrowed down to the exact failing
statement in this triage pass — needs a follow-up investigation session
(isolate by bisecting the routine body) before a fix brief can cite a line.
**Feasibility: unknown pending that investigation** — flagged, not judged.

### Finding E — UNIQUE-1219: MySQL local-variable `SET` misclassified as a session setting → **structural SQL corruption**, not just a degrade (mysql `func2`, `proc_6`)

This is the most severe finding in the corpus and should be treated as
higher priority than its 2-routine count suggests. The gate at
`src/unique/core/transpiler/_core.py:2010`:

```python
or re.match(r"(?is)^\s*SET\s+[A-Za-z_][\w.]*\s*=", code)
```

is meant to catch top-level/batch-level MySQL session knobs (`SET sql_mode
= ...`) but MySQL uses the **identical syntax** for local-variable
assignment inside a routine body (`SET v_col_88 = REPLACE(...)`). Live
reproduction on `func2` (31 statements in its body): after the first two
`SET` assignments transpile correctly, every subsequent `SET var = expr;`
line individually triggers this gate and — critically — the gate's
`TranspileResult` appears to be produced in a way that **closes the
enclosing function early**. The actual emitted output:

```sql
CREATE OR REPLACE FUNCTION func2 (...)
...
BEGIN
    ...
    v_mod := CASE ... END;
END;
$$;                                          -- function closes here, ~28 statements early

-- UNIQUE-1219: MySQL session setting has no postgresql equivalent...
-- SET v_col_88 = REPLACE(...)
...
"END" AS IF;                                  -- INVALID top-level SQL
...
"END";                                        -- INVALID top-level SQL
```

The remaining ~28 statements (including the function's actual `RETURN
func4(...)`) leak **outside** the `$$ ... $$` body as top-level
carrier-commented fragments, and two syntactically invalid bare statements
(`"END" AS IF;`, `"END";`) appear in the output. This is not a documented,
honest degrade — it is corrupt PostgreSQL that would fail to load. Given
this repo's "never ship invalid output silently" guardrail, this is a P0/P1
correctness bug independent of its routine count. **Recommend a dedicated,
first-priority brief**, separate from the coverage-ranking below.

### Finding F — UNIQUE-1230 / UNIQUE-1231: code-fidelity gap, not a mechanism

`src/unique/core/transpiler/_core.py:919-926` (procedural **parse**
warnings) and `:955` (procedural **transform** warnings) stamp every
`ProceduralParser`/`ProceduralTransformer` warning string with a flat
generic code (`UNIQUE-1230` / `UNIQUE-1231` respectively) at emission time —
before the batch-level "no-silent-loss" reconciliation (`_core.py:748-780`)
runs, which only back-fills a carrier's specific code onto a warning whose
`.code is None`. Since these warnings already have a (wrong, generic) code
by then, they never get corrected to the specific code that's actually
embedded in the carrier comment the same transform produced (e.g. a routine
whose carrier text says `-- UNIQUE-1171: ...` reports `UNIQUE-1231` in
`result.warnings[].code`). Confirmed live on `proc_1` (mysql): `.warnings`
carries `code=UNIQUE-1231`, `message="MySQL user variable @col_2 has no
postgresql equivalent; routine preserved as a comment"` — the identical text
that appears in the SQL as `-- UNIQUE-1171: ...`.

This does not affect the shipped SQL (the carrier text a human reads is
already correct); it affects **any consumer of `.warnings[].code`** — which
now includes F1's `SimilarityReport.warnings` (`docs/TODO.md` F1 brief,
landed 2026-07-30) and any future code-based tooling. Low routine-count
impact but cheap to fix and improves the accuracy of every future
code-frequency triage like this one (this Q1 pass had to work around it by
diffing against `source_codes`, which won't be available for a live
non-fixture script).

## Reproduction

The triage script (not committed — scratch, ad hoc) split each fixture via
`BatchSplitter.split(text, dialect)`, filtered `PROCEDURAL` batches matching
`CREATE\s+(OR\s+REPLACE\s+)?(PROCEDURE|FUNCTION)\s+(\w+)` (last match wins
per batch), and ran `Transpiler().transpile(routine_sql, source,
"postgresql")` per routine, diffing `UNIQUE-\d{4}` codes found in
`result.warnings[].code` ∪ output-text regex matches against the same codes
found in the routine's pre-transpile source text.
